# Disposable SSH runtime and access oracle

Status: development verification for v5.00.0. Refs #235, #337 and #422.
This oracle qualifies a test fixture, not an installed migration or package.

## Scope and isolation

The opt-in `TestOpenSSHRuntimeAccessOracle` starts two disposable OpenSSH daemons
on random IPv4 loopback ports: a target and an independent forwarding bastion.
It uses the installed `ssh`, `sshd` and `ssh-keygen` binaries as an ordinary local
test account. It does not use the installed SSH configuration, service manager,
operator keys, SSH agent, existing authorized keys or a production endpoint.

Each profile receives newly generated Ed25519 client and host keys. All fixture
files live in a private temporary directory directly under the test account's
home. OpenSSH `StrictModes` remains enabled; using `/tmp` for authorized keys
would fail its ancestor checks. Cleanup removes only that generated directory
and stops the disposable daemon groups. The original child remains unreaped
until group cleanup, preventing its PID from being reused before cleanup.
Reload signals use retained pidfds without a numeric-PID fallback.

A fixed client configuration pins both host keys, disables connection sharing
and agents, restricts authentication to the generated key, and bypasses ambient
SSH configuration. Every access probe starts a new client process and requires
the exact response to a fresh random challenge. The ProxyJump path uses the same
controlled client configuration. No bastion is automatically detected, selected
or reconfigured.

## Required observations

For both the forwarding and CIS candidates:

1. Authenticate directly and through the fixture bastion. Reject an unauthorized
   client key and an unpinned server identity.
2. Confirm that target TCP forwarding works before publication. Retain a
   separately authenticated forwarding channel as a negative control.
3. Publish the generated drop-in into the fixture. The installed parser must
   accept it and report all candidate values. Fresh forwarding must still work
   before the daemon reloads, despite those new effective parser values.
4. Send one pidfd `SIGHUP` and wait for the fixture's new listener announcement.
   Fresh forwarding must now fail specifically as administratively prohibited.
   The existing channel must still answer, demonstrating why it cannot prove
   the behavior of a fresh connection.
5. Authenticate again directly and through the unchanged bastion. Withdraw only
   the target fixture's authorized key: the bastion must remain accessible while
   fresh target authentication fails on both routes. Restore the fixture key and
   require fresh authenticated responses again.
6. Restore the inactive fixture drop-in. Fresh forwarding must remain refused
   until a separate fixture reload, then work again. Authenticate on both routes
   after that reload.

The private [fresh access transport](SSH_FRESH_ACCESS_PROBE.md) is also exercised
through the [approved request batch](SSH_PROTECTED_ACCESS_REQUEST.md)
twice on each route after candidate reload. Its challenge and SSH session hashes
must change between calls, with separately authenticated bastion sessions. The
fixture supplies synthetic bindings; this does not validate controller enrollment
or protected production transaction state.

The oracle checks actual TCP-forwarding behavior. It does not claim runtime
verification of every CIS directive merely because the parser reports its value.
The target policy is generated by `Prepare`, but fixture writes and reloads are
not the production publication transaction or systemd activation adapter.
The daemon log is a fixture startup synchronizer, not a production causal
acknowledgement or proof of the entire consumed configuration.

## Running and interpreting the oracle

Run on Linux AMD64 with an ordinary local test account that can authenticate
using public keys with `UsePAM no`. Its home and ancestors must satisfy OpenSSH
ownership checks. Do not change account security or installed SSH settings to
make this test pass. Missing tools, a locked account, unavailable pidfds,
configuration refusal or a failed connection is a failure when explicitly
requested, not a skipped success.

From `src/core/syswarden-cli`:

```sh
SYSWARDEN_SSH_RUNTIME_ORACLE_TEST=1 GOMAXPROCS=2 \
  go test -count=1 -race -timeout=3m \
  -run '^TestOpenSSHRuntimeAccessOracle$' -v ./pkg/sshpolicy
```

The fixture lifetime is bounded to one minute per profile; individual commands
and listener waits have shorter deadlines. Output-pipe draining is also bounded.
Normal unit-test runs skip this opt-in test. Hosted unit-test success alone does
not establish that this native oracle ran. Keep the explicit command, installed
OpenSSH identity and complete result with private validation evidence.

OpenSSH documents daemon re-execution on `SIGHUP` in the
[daemon manual](https://man.openbsd.org/sshd), and separate client identity,
connection-sharing and ProxyJump settings in the
[client configuration manual](https://man.openbsd.org/ssh_config).

## Remaining production gates

This is intermediate native evidence within the v5.00.0 IVVQ campaign, not final
acceptance. The production controller still needs independently authenticated
fresh access bound to the approved transaction, causal policy-consumption
acknowledgement, runtime-aware recovery, already-owned updates and separately
validated native uninstall, remove and purge paths. Native distribution,
service-manager, authentication and administrator-environment matrices remain
open. A migration-ready package is not yet available.

Issue #422 remains mandatory: fresh native packages use only the standard list;
SSH, CIS, OS hardening and optional modules require independent explicit TOML
choices. Upgrades preserve administrator configuration and existing protection.
The source installer uses the minimal profile, while [native dependency
transitions and package qualification](MINIMAL_NATIVE_INSTALL.md) remain open. This oracle
does not alter defaults or bypass approval and recovery fences. BunkerWeb's
independent contract is unchanged; the product scope remains Linux AMD64 only.

## Signed observation path

The oracle now runs the [signed controller path](SSH_CONTROLLER_RECEIPTS.md)
using a newly generated fixture controller key and approved challenge. It
verifies the exact signed batch before comparing fresh target/bastion sessions.
The signed result retains recovery required. These fixture approvals do not
establish production enrollment, durable receipt acceptance or native migration.
