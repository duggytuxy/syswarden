# Explicit trust for service-owned log inputs

Status: development correction for [issue #390](https://github.com/duggytuxy/syswarden/issues/390).
The stable release remains v4.10.4. Component checks do not establish native
container compatibility or final v5.00.0 IVVQ acceptance.

## Authorization boundary

A legitimate WAF or web service can write its logs as a dedicated non-root UID.
The default collector policy still rejects an unexpected owner. Do not make a
service root, change its log ownership to root, or grant trust to every account
to bypass that refusal.

An administrator may explicitly bind an exact collector-visible path to its
producer UID in the root-controlled modular configuration:

```toml
[waap]
trusted_log_producers = "/var/log/example-waf/audit.log=999 /srv/example-web/access.log=100999"
```

These are illustrative UIDs, not product defaults or recommendations. Verify the
actual UID and directory ownership in the collector's namespace before creating
a grant. A container image name, service name, numeric UID observed in an error,
or a UID inside a different user namespace does not establish trust. A remapped
container UID must be translated and verified at the collector boundary.

Each grant authorizes that producer to supply security-relevant input. A
compromised authorized service can forge its own log contents; metadata checks
do not authenticate application statements. Client-controlled text within a
legitimate log remains untrusted detection input. Keep source authentication,
rule validation and false-positive review independent.

The legacy equivalent is `SYSWARDEN_TRUSTED_LOG_PRODUCERS`. Migration preserves
its explicit value and creates no grants by default. Both CLI and core reject
malformed policies. At most 32 exact paths and 16 KiB of policy text are allowed.
Globs, duplicate paths, noncanonical spacing, relative paths, UID zero, the
unmapped UID 65534, and the invalid UID sentinel are rejected. Root-owned files
continue through the existing service authority without a separate root grant.
The runtime never infers a new grant from current file ownership.

## Collection and rotation

With at least one grant configured, the secure core follower owns all file inputs
previously collected by the generated rsyslog WAF bridge, including its web and
system/authentication defaults. The configured ModSecurity and brute-force
sources remain part of collection, and each exact granted path is enrolled too.
The generated bridge has no generic imfile detection inputs in this mode, so an
old wildcard cannot bypass ownership checks after rotation. Optional SIEM export
of SysWarden's native telemetry remains separate. With no grants configured, the
historical bridge rendering remains unchanged.

The CLI verifies existing sources before reconciling the bridge. Every directory
is opened without following symlinks; its owner must be root, the collector or the
explicit producer for that file. Writable immediate parents are refused. Files
must be regular, singly linked and not writable by group or others. Special
permission bits and wrong owners are refused. A grant for one file does not
apply to another file in its directory or to all logs from the same UID.

The core repeats validation when opening a file and after rotation. It monitors
the held inode for ownership and permission changes, permits draining a verified
unlinked rotation inode, and checks that the configured parent still names the
pinned directory before adopting a replacement. Unsafe replacements stop that
follower with an explicit diagnostic. Nothing is silently adopted, chmodded or
chowned. Discovery occurs at startup; a missing or refused input requires
operator correction and a verified restart/reload, not a claim of full coverage.

Apply the policy with the normal verified `syswarden reload` sequence. A bridge
reconciliation failure prevents activation of the new producer policy during
that sequence. Review its errors before retrying. Starting only the core binary
manually is not a substitute for the bridge transition. Administrator-created
rsyslog inputs are neither modified nor claimed by this policy; review any
independent duplicate ingestion paths separately.

## Integration and lifecycle scope

This concerns local file ingestion. It does not change BunkerWeb's independent
synchronization API, temporary ban durations, source ownership, HA behavior,
firewall rules or the dashboard contract. Existing parser and detection controls
still apply to every accepted line.

External service logs remain administrator/application data. Uninstall, package
remove and package purge must preserve them and unrelated rsyslog configuration.
Only the generated bridge and its exact provenance follow the existing product
removal contract. Historical generated bytes stay available for exact recovery;
a filename or producer grant is not deletion authority.

Component coverage includes configuration migration and CLI/core parity,
explicit-owner rotation, malformed grants, unsafe file or parent substitution,
hardlinks, special files and a failed bridge transition. Native acceptance still
requires actual service-owned logs, applicable user namespace mappings, mandatory
access controls, service reload/reboot, and separate uninstall/remove/purge
preservation checks. Keep issue #390 open until that evidence is available.
