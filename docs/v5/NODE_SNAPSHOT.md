# v5 node identity and read snapshot

Status: second executable WP02 slice for review. Refs #224, #233 and #315.
This is a development contract, not an enrollment service or an enabled fleet
API. The stable release remains v4.10.4.

## Identity is independent of location and connectivity

The [node contract](../../src/core/syswarden-core/contracts/v5/node.go) defines
`NodeIdentity` as an exact triple: `cluster_id`, `node_id` and `epoch`. All three
are required bounded opaque identifiers, with the same ASCII grammar as the
[event envelope](EVENT_ENVELOPE.md). No value is generated by this package.

An authenticated membership registry must assign and approve the triple. An
address, hostname, event label or self-reported identifier does not enroll a
node. Replacing an address must not silently replace a node's identity. The
cluster is a membership domain; its label does not prove membership of an HA
writer group or permission to synchronize bans.

The epoch is an opaque membership generation. Comparison uses exact equality,
including case. Neither a numerically larger value nor a lexically later value
can replace the expected epoch. The caller must obtain the expected identity
from its current authorized registry, never from the document it is checking.
Updating that registry is a separate authenticated and audited operation.

Issuance, key binding, rotation, revocation, enrollment, replay protection and
registry recovery remain WP11 work. This schema does not implement them. A
comparison with an obsolete trusted registry can still accept obsolete data;
the registry's lifecycle cannot be replaced by a string comparison.

## Snapshot semantics

`syswarden.node-snapshot.v1` is one collector statement about one managed node.
It is not a node list, an implicit discovery request or a response command.
Its independent references must be resolved through future scoped contracts.

| Field | Meaning |
| --- | --- |
| `snapshot_id` | Caller-assigned stable record identifier. It does not implement deduplication or ordering by itself. |
| `identity` | Exact expected cluster/node/generation tuple. |
| `collector_id` | Collector reference, whose authenticity and authorization require separate verification. |
| `collected_at` | Collector time for the exchange or observation attempt. |
| `valid_until` | Exclusive limit on considering this collector report current. |
| `reachability` | `reachable`, `unreachable` or `unknown`; a transport observation, never a protection verdict. |
| `last_successful_contact` | Collector-established contact time, or an explicit availability state. It cannot be later than collection. |
| `observed_at` | Optional source observation time; it cannot extend the collector freshness window. |
| `clock_quality` | Reported `unknown`, `synchronized` or `unsynchronized`, with explicit availability. |
| `agent_version` | Bounded version label, not proof of installed or signed software. Version comparison and package attestation are not implemented here. |
| `policy_ref`, `control_ref` | Independent policy and protection evidence references, never inferred from reachability. |
| `integration_ref` | Independent integration-state reference. Its name alone cannot enable synchronization or establish partner presence. |

All fields are mandatory, and availability uses the seven states defined by the
event envelope. Missing or unavailable data carries an empty value. Partial and
stale data retain a nonempty value, visibly distinguished from present data.

For `reachable`, the last successful contact must be `present` and equal to
`collected_at`. This represents the actual successful exchange, not a later
rendering of a cache. Rendering or re-serving a cached report must retain its
original times, rather than extend its validity.

For `unreachable` or `unknown`, retained source observation time, clock quality,
agent version and all three evidence references must be `stale`. Their absence
may instead be represented explicitly. A new outage report cannot renew old
agent evidence. The last successful contact remains a historical collector
fact and may retain its original value.

A reachable server may still have unavailable or rejected protection evidence.
A current report of a disconnection may still retain stale evidence that the
server was protected. Neither condition establishes the current enforcement
state. The decoder does not replace a reference with an invented verdict.

## Freshness and trust are separate checks

`DecodeNodeSnapshot` and `EncodeNodeSnapshot` apply bounded strict JSON and
internal coherence checks. They intentionally permit reading an expired record
for an explicitly historical or stale view. Decoding alone does not establish
that a record is current.

`CheckCurrentNodeSnapshot` additionally takes a `NodeReadContext` with expected
membership, an explicit caller time and an explicit maximum age. There is no
implicit `time.Now` or permissive default. The accepted interval is:

```text
[collected_at, min(valid_until, collected_at + caller_max_age))
```

The exact expiry instant is rejected. A caller's shorter maximum age takes
precedence; a broader age cannot extend the document's expiry. Source clock
skew cannot extend this interval. A future collector timestamp is not current.
The wire lifetime and caller age each have a 24-hour hard ceiling. This ceiling
is an initial schema safety bound, not the operational freshness target. The
reviewed deployment policy must choose appropriate shorter windows, consistent
with the workload and freshness budgets that remain open in WP01.

A current report of an outage passes the contextual time/identity check while
its retained agent facts remain stale. Current report does not mean current
protection evidence. Callers still need authenticated collection, scope checks,
evidence verification, replay/deduplication state and a trustworthy local clock.
The helper has no side effects and cannot grant read or response authority.

## Encoding and migration boundary

The existing event parser's 16-KiB byte limit, depth/member/value bounds,
duplicate-key rejection, strict field spelling and Unicode checks also apply
here. Every field is explicit; nulls, unknown members, malformed identities and
unsupported schemas are rejected with no partially usable snapshot. Errors do
not echo untrusted identifiers or payloads.

Encoding is compact JSON in declared field order with no final newline, pinned
by synthetic golden vectors. It is schema-specific, not JCS or a signed proof.
No address list, map coordinates, arbitrary label map, credentials or raw logs
are included in this first node schema.

No automatic v4 node-identity migration is provided. The frozen v4 event input
has no approved cluster/node/epoch tuple. Tests reject those six records as
node snapshots rather than manufacturing enrollment. The existing conservative
event projection is unchanged. Even a v5 event's plain node reference is not
membership proof or an epoch binding; authenticating and binding historical
events remains separate ingestion work.

## BunkerWeb and remaining acceptance

The [BunkerWeb compatibility boundary](BUNKERWEB_COMPATIBILITY.md) remains
unchanged. This package has no runtime consumer and makes no network, service
or firewall changes. The existing plugin API, TTL/source ownership, HA fencing
and log ingestion remain independent of the planned dashboard.

A retained integration reference is not dropped because its node is
unreachable. This prepares the known-but-unavailable dashboard state. Resolving
that reference, establishing log-only/sync/combined participation, checking
scope and deciding tab visibility still require a dedicated authoritative
integration contract. This schema does not enable the tab or synchronization.

Tests cover exact generation binding, missing identities, address substitution,
clock skew, expiry boundaries, local age policy, stale caches, reachable nodes
without protection evidence, malformed documents, legacy rejection and golden
encoding. A bounded fuzz target is included in the existing security workflow.

WP02 and WP11 remain open. The other schemas, authenticated ingestion,
membership lifecycle, authorization, replay handling, shared consumer adapters,
maps, rate indicators and native migration evidence are not completed by this
slice. No real partner IVV or fleet capacity claim is made.
